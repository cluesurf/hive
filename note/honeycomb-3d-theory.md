# 3D Hyperbolic Honeycomb Theory and Implementation

Analysis of the Hyperbolic-Honeycombs reference implementation and how
to apply it to our codebase.

## Overview

The reference implementation (neozhaoliang/Hyperbolic-Honeycombs) uses a
fundamentally different approach from our current code:

| Aspect          | Reference Implementation        | Current Implementation         |
| --------------- | ------------------------------- | ------------------------------ |
| Model           | Hyperboloid (Minkowski R^{3,1}) | Poincare ball directly         |
| Rendering       | GPU ray marching (SDF)          | CPU mesh generation            |
| Cell definition | Coxeter reflection mirrors      | Explicit dodecahedron vertices |
| Generalization  | Any {p,q,r} honeycomb           | Only {5,3,4} (dodecahedral)    |
| Geodesics       | Implicit in SDF                 | Explicit arc calculation       |

## The Hyperboloid Model in 4D

### Minkowski Space R^{3,1}

The hyperboloid model embeds 3D hyperbolic space H^3 in 4D Minkowski
space:

```
Point p = (x, y, z, w) where x^2 + y^2 + z^2 - w^2 = -1, w > 0
```

### Minkowski Inner Product

```glsl
// Signature (3, 1): three positive, one negative
float hdot(vec4 p, vec4 q) {
    return dot(p.xyz, q.xyz) - p.w * q.w;
}
```

Key properties:

- Points on hyperboloid: `hdot(p, p) = -1` (timelike vectors)
- Reflection mirrors: `hdot(n, n) = 1` (spacelike vectors)
- Ideal points: `hdot(p, p) = 0` (lightlike/null vectors)

### Normalization

For timelike vectors (points):

```glsl
vec4 hnormalize(vec4 p) {
    return p / sqrt(-hdot(p, p));
}
```

## Poincare Ball to Hyperboloid Conversion

### Lifting a 3D Point to 4D Hyperboloid

For a point p in the Poincare ball with r = |p|:

```glsl
float r = length(p);
vec4 q = vec4(2.0 * p, 1.0 + r*r) / (1.0 - r*r);
```

This maps:

- Origin (0,0,0) to (0,0,0,1) on the hyperboloid
- Points near boundary (r near 1) to large w values
- The entire open ball to the upper sheet of the hyperboloid

### Projection Back to Poincare Ball

```glsl
vec3 toBall(vec4 q) {
    return q.xyz / (1.0 + q.w);
}
```

## Coxeter Groups and Reflection Mirrors

### The Fundamental Domain

A {p,q,r} honeycomb is generated by a Coxeter group with 4 reflection
mirrors. The mirrors are hyperplanes in 4D Minkowski space, defined by
their normal vectors A, B, C, D.

### Dihedral Angles from Schlafli Symbol

The angles between adjacent mirrors are derived from the Schlafli
symbol:

```
Mirror pair | Angle | Relation to Schlafli
-----------|-------|----------------------
A-B        | pi/AB | Where AB comes from {AB, AC, AD, BC, BD, CD}
A-C        | pi/AC | Typically AB=p, BC=q, CD=r for {p,q,r}
A-D        | pi/AD | Non-adjacent pairs often have angle pi/2 (value 2)
B-C        | pi/BC |
B-D        | pi/BD |
C-D        | pi/CD |
```

For {p,q,r} honeycombs, the standard encoding is:

- AB = p (polygon sides)
- BC = q (polygons per edge)
- CD = r (cells per edge)
- AC = BD = 2 (orthogonal pairs)
- AD = 2 (orthogonal)

### Computing the Mirror Normals

The initialization computes mirrors A, B, C, D:

```glsl
void init() {
    // Cosines of dihedral angles (negative because mirrors face inward)
    float c01 = -cos(PI / float(AB));  // cos(angle between A and B)
    float c02 = -cos(PI / float(AC));
    float c03 = -cos(PI / float(AD));
    float c12 = -cos(PI / float(BC));
    float c13 = -cos(PI / float(BD));
    float c23 = -cos(PI / float(CD));

    vec4 A, B, C, D;

    // A is chosen along x-axis (arbitrary but consistent)
    A = vec4(1, 0, 0, 0);

    // B makes angle arccos(c01) with A
    B = vec4(c01, sqrt(1.0 - c01*c01), 0, 0);

    // C is determined by its angles with A and B
    C = vec4(c02, 0, 0, 0);
    C.y = (c12 - C.x * B.x) / B.y;
    C.z = sqrt(abs(1.0 - dot(C.xy, C.xy)));

    // D is in 4D, with negative w to stay in upper sheet
    D = vec4(c03, 0, 0, 0);
    D.y = (c13 - D.x * B.x) / B.y;
    D.z = (c23 - dot(D.xy, C.xy)) / C.z;
    D.w = -sqrt(abs(dot(D.xyz, D.xyz) - 1.0));  // Negative for upper sheet
}
```

The key insight: D.w is negative, making D a spacelike vector that
defines a reflection hyperplane intersecting the hyperboloid.

## The Folding Algorithm

### Core Concept

Instead of generating cells explicitly, the algorithm:

1. Takes any point in the Poincare ball
2. Lifts it to the hyperboloid
3. Repeatedly reflects until it lands in the fundamental domain
4. Measures distance to cell features (vertices, edges, faces)

### Reflection in Minkowski Space

```glsl
float try_reflect(inout vec4 p, in vec4 n) {
    float k = min(0.0, hdot(p, n));  // Only reflect if on wrong side
    p -= 2.0 * k * n;                 // Householder reflection
    return k;                         // Returns 0 if no reflection needed
}
```

### The Fold Loop

```glsl
bool fold4d(inout vec4 p) {
    float k;
    for (int i = 0; i < Iterations; i++) {
        k = 0.0;
        p.x = abs(p.x);               // Reflect across A (x=0 plane)
        k += try_reflect(p, M[1]);    // Reflect across B
        k += try_reflect(p, M[2]);    // Reflect across C
        k += try_reflect(p, M[3]);    // Reflect across D
        if (k == 0.0) return true;    // In fundamental domain
    }
    return false;  // Didn't converge
}
```

After folding, the point is in the fundamental domain and we can measure
distances to the canonical cell features.

## Distance Estimation

### The Knighty Distance Formula

The critical function `knightyDD` converts hyperbolic distance to
Euclidean distance for ray marching:

```glsl
// Given cosh(d) = ca, sinh(d) = sa, and r = |p| in Poincare ball
float knightyDD(float ca, float sa, float r) {
    float x = 1.0 + r * r;
    float y = 2.0 - x;
    return (2.0 * r * ca + x * sa) / (x * ca + 2.0 * r * sa + y) - r;
}
```

This is derived from projecting the hyperbolic distance back to 3D.

### Distance to Vertex

```glsl
float dVertex(vec4 p, float r) {
    // Hyperbolic distance from p to vertex v0
    float ca = -hdot(p, v0);  // cosh(distance)
    float sa = 0.5 * sqrt(-hdot(p - v0, p - v0) * hdot(p + v0, p + v0));

    // Subtract vertex radius and convert to Euclidean
    return knightyDD(ca * cvr - sa * svr, sa * cvr - ca * svr, r);
}
```

### Distance to Edge (Geodesic Segment)

For an edge defined by vertex v0 and mirror normal n:

```glsl
float dSegment(vec4 p, vec4 n, float r) {
    // Project p onto the geodesic defined by v0 and n
    float pn = hdot(p, n);
    float pv = hdot(p, v0);
    float nv = hdot(n, v0);
    float det = -1.0 - nv * nv;
    float a = (-nv * pv - pn) / det;
    float b = (pv - pn * nv) / det;

    // Closest point on geodesic
    vec4 pj = hnormalize(min(a, 0.0) * n + b * v0);

    // Distance and convert
    float ca = -hdot(p, pj);
    float sa = 0.5 * sqrt(-hdot(p - pj, p - pj) * hdot(p + pj, p + pj));
    return knightyDD(ca * csr - sa * ssr, sa * csr - ca * ssr, r);
}
```

### The Complete Distance Estimator

```glsl
float DE(vec3 p) {
    float r = length(p);

    // Lift to hyperboloid
    vec4 q = vec4(2.0 * p, 1.0 + r*r) / (1.0 - r*r);

    // Fold into fundamental domain
    bool found = fold4d(q);

    // Distance to cell features
    float dV = dVertex(q, r);   // Vertices (balls)
    float dS = dSegments(q, r); // Edges (tubes)
    float dF = dFaces(q, r);    // Faces (sheets)

    // Clip to Poincare ball boundary
    return max(r - CSphRad, min(dF, min(dV, dS)));
}
```

## Why the Current Implementation is Incorrect

### Problem 1: Fixed Dodecahedron Shape

The current code uses a Euclidean dodecahedron scaled and placed:

```typescript
// This is WRONG for hyperbolic cells
const PHI = (1 + Math.sqrt(5)) / 2
function getDodecahedronVertices(): Vec3[] {
  // Euclidean dodecahedron vertices...
}
```

In hyperbolic space, a dodecahedral cell has a different shape depending
on the honeycomb. The {5,3,4} cell is not a scaled Euclidean
dodecahedron.

### Problem 2: Incorrect Neighbor Distance

```typescript
// This formula is heuristic, not mathematically correct
const faceRatio = 0.7946 // inradius/circumradius for Euclidean dodecahedron
const f = cellRadius * faceRatio
const neighborDist = (2 * f) / (1 + f * f)
```

The correct neighbor distance depends on the specific {p,q,r} honeycomb.

### Problem 3: Approximate Geodesic Arcs

The geodesic arc calculation is complex and error-prone. The ray
marching approach avoids this entirely.

### Problem 4: No Generalization

The code only works for {5,3,4}. Changing p, q, r parameters has no
effect.

## Correct Approaches

### Option A: GPU Ray Marching (Like Reference)

Port the GLSL to WebGL/Three.js shader:

- Pros: Accurate, fast, handles any {p,q,r}
- Cons: Requires shader knowledge, harder to debug

### Option B: CPU Mesh with Correct Cell Geometry

Use the Coxeter group to compute exact cell geometry:

- Compute fundamental domain from mirrors
- Generate vertices by orbit of a vertex under the group
- Build mesh from vertices and edges
- Pros: Works with Three.js mesh pipeline
- Cons: Complex vertex generation, slower

### Option C: Hybrid Approach

Use CPU for cell structure, GPU for rendering:

- CPU computes cell centers and transforms
- GPU renders each cell with a local SDF shader
- Pros: Combines best of both
- Cons: Most complex to implement

## Key Formulas Summary

### Hyperbolicity Condition

For {p,q,r} honeycomb to be hyperbolic:

```
1/p + 1/q + 1/r < 1
```

### Hyperbolic Cosine Rule

For a hyperbolic cell with {p,q} faces:

```
cosh(edge) = cos(pi/p) * cos(pi/q) / sin(pi/p) / sin(pi/q)
```

### Cell Inradius

```
cosh(inradius) = cos(pi/p) / sin(pi/q)
```

### Cell Circumradius

```
cosh(circumradius) = cos(pi/q) / sin(pi/p)
```
