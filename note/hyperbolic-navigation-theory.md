# Hyperbolic Navigation Theory

## The Problem

We want to navigate infinitely through a 3D hyperbolic honeycomb. The
user scrolls or uses WASD to "move" through the space, and the honeycomb
should continuously unfold around them as they travel.

## The Poincaré Ball Model

The Poincaré ball model maps all of infinite 3D hyperbolic space H³ into
the interior of a unit ball in Euclidean space:

- Points at the origin are "here"
- Points near |p| = 1 are infinitely far away
- The boundary |p| = 1 represents "infinity"

This is analogous to how the 2D Poincaré disk maps infinite 2D
hyperbolic space into a unit circle.

## The Honeycomb Structure

The {p,q,r} honeycomb is defined by:

1. A fundamental domain (a tetrahedron in the hyperboloid model)
2. Four reflection mirrors A, B, C, D
3. The Coxeter group generated by reflections across these mirrors

The honeycomb is always "centered" at a specific point. In our
implementation, it's centered at the origin of the Poincaré ball.

## The Navigation Challenge

When the user "moves forward", we have two options:

### Option A: Move the Camera (Current Broken Approach)

Move the camera position within the Poincaré ball and transform sampled
points.

Problems:

- The distance estimator DE(p) expects points in the honeycomb's
  coordinate system (centered at origin)
- Transforming points via Möbius addition during ray marching causes
  inconsistencies
- The folding algorithm assumes the honeycomb is at origin
- Numerical precision issues near the ball boundary

### Option B: Re-center the Honeycomb (Correct Approach)

Keep the camera at the origin and apply a Möbius isometry to the entire
honeycomb. This is mathematically equivalent to moving through space.

How it works:

1. Camera always stays at origin (0, 0, 0)
2. Track a "virtual position" that represents where we've traveled
3. Before computing DE(p), transform p by the inverse of our virtual
   position
4. This shifts the honeycomb so that our destination appears at the
   origin

## Möbius Transformations as Isometries

In the Poincaré ball, Möbius transformations preserve hyperbolic
distances. A translation by vector a is:

```
T_a(p) = a ⊕ p = ((1 + 2⟨a,p⟩ + |p|²)a + (1 - |a|²)p) / (1 + 2⟨a,p⟩ + |a|²|p|²)
```

The inverse translation (moving the honeycomb instead of the camera):

```
T_{-a}(p) = (-a) ⊕ p
```

## Correct Implementation Strategy

### Step 1: Track Virtual Position

Maintain a "virtual position" vector that accumulates as the user moves:

```typescript
// In navigation state
virtualPosition: THREE.Vector3 // Accumulated position via Möbius addition
```

When user moves forward by direction d with speed s:

```typescript
const translation = d.multiplyScalar(Math.tanh(s / 2))
virtualPosition = mobiusAdd(virtualPosition, translation)
```

### Step 2: Transform in the Shader

In the fragment shader, transform each sampled point by the inverse of
virtualPosition BEFORE calling the distance estimator:

```glsl
// Transform point from view space to honeycomb space
vec3 toHoneycombSpace(vec3 p) {
    return mobiusAdd(-cameraPos, p);  // -cameraPos is the inverse translation
}

// In ray marching loop:
vec3 p = t * rayDir;                    // Point in view space (camera at origin)
vec3 pHoneycomb = toHoneycombSpace(p);  // Point in honeycomb space
float d = DE(pHoneycomb);               // DE expects honeycomb-space coordinates
```

### Step 3: Keep Ray Marching View-Centered

The ray marching itself stays simple:

- Camera is always at origin
- Rays go out from origin in view direction
- Each point along the ray is transformed to honeycomb space for DE
  evaluation

### Step 4: Handle Normals and Coloring

For shading, we need to be careful:

- Normals should be computed in honeycomb space (where DE is defined)
- But lighting calculations use view-space directions
- Colors come from honeycomb-space positions

```glsl
vec3 pHoneycomb = toHoneycombSpace(hitPos);
vec3 normal = estimateNormal(pHoneycomb);  // Honeycomb space
vec3 color = getColor(pHoneycomb);         // Honeycomb space
vec3 viewDir = normalize(-hitPos);         // View space (toward camera at origin)
```

## Why This Works

1. The honeycomb is always computed relative to its natural origin
2. The Möbius transformation is a hyperbolic isometry, so distances are
   preserved
3. The camera stays at the Poincaré ball origin, avoiding boundary
   issues
4. The virtual position can grow arbitrarily (it's just a parameter for
   the transformation, not an actual position that must stay in the
   ball)

## Edge Cases

### Large Virtual Positions

As virtualPosition approaches |v| → 1, the Möbius transformation becomes
extreme. However, this is mathematically correct. The transformation
T\_{-v}(p) will map points from far away to near the origin.

For numerical stability, we may want to periodically "re-center" by:

1. Finding which cell of the honeycomb we're in
2. Resetting virtualPosition to the equivalent position in that cell
3. This exploits the honeycomb's symmetry

### Rotation

Rotation is separate from translation in hyperbolic space. We handle it
by:

1. Tracking yaw/pitch angles
2. Building the view direction from these angles
3. Rays are cast in the rotated direction

Rotation doesn't require Möbius transformation - it's just changing
which direction we look.

## Alternative: Gyrovector Velocity

Instead of accumulating position, we could track velocity and integrate:

```
position(t+dt) = position(t) ⊕ (velocity * dt)
```

This might give smoother movement but is mathematically equivalent.
